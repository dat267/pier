# Reproduced audit findings
- **A542, low:** a package filter object set through the API is saved with its keys sorted. pi v1.5.2 (b4afdddf) stores package sources as JavaScript objects, so `setProjectPackages([{source: "pkg-b", skills: ["s"]}])` writes `{"source":...,"skills":[...]}` in that order. `coding/settingsmanager.go` `SetPackages`/`SetProjectPackages` take `[]any`, so the caller's object is already a Go map and the write sorts it (`{"skills":...,"source":...}`). No production caller sets packages (the package manager is out of scope, D-rows), so this is reachable only through the library API; a faithful fix needs an order-preserving input (raw JSON or an ordered object), which is an API decision.
- **A543, unconfirmed:** under `go test ./coding/interactive -count=3 -shuffle=on` a renderer parity test occasionally draws an empty expand-hint key label, which means `tui.GetKeybindings()` returned a manager without the app ids partway through a test that had just installed the app manager. Two failing runs showed it in different tests (`TestBashToolRenderUpstreamParity` `narrow@40`, `TestSearchToolRenderUpstreamParity` `grep-many-lines@80`); five further shuffled runs with a probe that logs an empty key set before each render did not reproduce it. The likely mechanism is a surviving worker from an earlier test calling `tui.SetKeybindings` (production code does so in `app.go` and `sessionpicker.go`), but no leak is visible at process exit. The parity tests now install their own keybindings, so the symptom is masked; find the writer before trusting a shuffled run.
