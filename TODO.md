# Reproduced, unresolved findings

## golang.org/x/image v0.30.0 carries three reachable WebP vulnerabilities

- Severity: low-medium. The crafted image must reach an image attachment path, so the attacker is whoever supplies the image (the user, or the model writing a file and reading it back).
- Affected: `coding/fileprocessor.go` `decodeInlineImage` (via `ProcessImage` -> `resizeInlineImage`) and `coding/imagetranscode.go`; the `webp` decoder is registered by the blank import at `coding/fileprocessor.go:15`.
- Failure: `govulncheck ./...` reports GO-2026-4961 (panic decoding a large WEBP on 32-bit), GO-2026-5061 (panic on a VP8 alpha-channel size mismatch) and GO-2026-6222 (excessive memory allocation during VP8L decoding, from many unused Huffman tree groups). The first two are contained: `decodeInlineImage` recovers panics and reports an error. The third is not recoverable: it exhausts memory before the `maxInlineImagePixels` canvas cap applies, because the allocation is in Huffman tables read from the header.
- Evidence: `govulncheck` output above; the vulnerability database lists fixes in v0.42.0, v0.43.0 and v0.45.0 respectively. The other six findings are in stdlib decoders pier never registers (TIFF, BMP, SFNT fonts), so they are unreachable.
- Repair plan: raise `golang.org/x/image` to v0.45.0 or later in `go.mod` and run `go mod tidy`; no code change is expected. Needs the user's decision because it installs a dependency.
## Auto-compaction uses a virtual model's window, not the routed model's

- Severity: low; no in-tree virtual model exists, so this only affects selections registered through the SDK.
- Affected: `coding/agent_session_virtual.go` `prepareVirtualRequest`, `coding/agent_session.go` `maybeAutoCompact`.
- Failure: upstream `core/agent-session.ts` checks `_exceedsCompactionThreshold(route.model, projection)` right after routing and compacts before the request continues. The port returns the routed model without that check, and its threshold hook (`maybeAutoCompact`, called from `PrepareNextTurnWithContext`) reads `s.Model()`, the virtual selection. The trigger therefore uses the virtual definition's `ContextWindow`: a virtual model registered with `ContextWindow: 0` never auto-compacts and recovers only from `CompactionOverflow` after a failed request, and one whose window differs from the routed model compacts at the wrong point.
- Evidence: read of `packages/coding-agent/src/core/agent-session.ts` (the `isVirtualModel` branch after `prepare()`) against `prepareVirtualRequest`; `maybeAutoCompact` runs before the routed request exists. The overflow path is not affected: `modelForMessage` resolves the physical model, so `sameModel` and the limits there are right.
- Repair plan: route, then compare `ProjectedContextEstimate().Tokens` with `route.Model.ContextWindow` through `ShouldCompact`, run `RunAutoCompaction(ctx, CompactionThreshold, false)`, and rebuild the messages before returning the update, as upstream's second `prepare()` does. Use a gated summarizer (the shape in `agent_session_compaction_state_test.go`) to pin that the routed model's window triggers compaction.

## A stress-gate run failed the RPC chaos test on a session write

- Severity: low until it is understood; it is a test failure in CI, not a confirmed product bug.
- Failure: in CI run 43827491162, the `race stress` step (`go test -race -count=2 -cpu=1,4 -shuffle=on -timeout 900s ./agent ./coding ./coding/interactive ./mcp`, shuffle seed 1794816114167051316) failed in `./coding`: `TestRPCAnswersEveryCommandOnceUnderAnInterleavedLoad` reported `the server stopped with session append failed (/tmp/TestRPCAnswersEveryCommandOnceUnderAnInterleavedLoad1767583622/003/other.jsonl): open .../other.jsonl: file exists`. A session manager whose file is missing records an uninitialized write state, so its first save claims the file with `O_EXCL`; the message means a claim found the file already there.
- Evidence: the CI log above. Not reproduced locally: one full `go test -race -count=2 -cpu=1,4 -shuffle=on ./coding` (green), one with the same seed (green), and six focused `-count=2 -shuffle=on` runs of the test (green). The test switches to one fixed path from a random 200-command stream, so the collision needs a particular interleaving.
- Refinement (audit round 11): upstream shares the throw. `_persist` in `core/session-manager.ts` creates the file with `openSync(sessionFile, "wx")` exactly once and lets an `EEXIST` escape, so the exclusive claim and its error are parity, not a port defect. What upstream does not have is a write queue shared between session managers: `rpcRuntime.newSessionManager`/`forkManager` pass `current.GetWriteQueue()` to the replacement, so a write enqueued for the outgoing manager can run against a path the incoming manager created. That is now the leading candidate, and the probe it needs is a log in `writeSessionEntriesExclusive` recording the path, the manager's session id and the enqueuing stack, then the stress loop.
- Confirmed ordering gap (audit round 11): neither replacement path drains the queue. `rpcRuntime.installSession` calls `settleWorkers` (which aborts the run and waits for `r.workers`) but never `FlushWrites`, and `interactive.App.teardownCurrentSession` likewise disposes without flushing. `FlushWrites` runs only at shutdown (`rpcmode.go:126`). Since `newSessionManager`/`forkManager`/`sessionNew` pass `current.GetWriteQueue()` to the replacement, a write enqueued for the outgoing manager can execute after the incoming manager is bound. No test asserts the ordering: `TestRPCSwitchSession` and `TestRPCForkBefore` read the new session, never the old file after the response. Proposed fix: `FlushWrites` in both replacement paths after settling, before the new manager is created. Test plan: share a queue, block its worker with a task, enqueue an append on the outgoing session, send `switch_session` from a goroutine, and assert the response does not arrive until the blocker is released and the old file holds the append.
- Repair plan: reproduce first. Run the stress command in a loop with `PIER_DEBUG_WRITE=1` and a temporary stack print in `SessionManager.recordWriteResult` (the message is built there), so the failing caller is known before anything is changed. Two candidates to check once reproduced: two managers opened on the same path before either writes it, or a queued write from the previous session landing after `switch_session` installed the new manager. `writeSessionState.rewrite` should then skip the exclusive claim when the file already exists, with a unit test that drives the reproducing sequence.

An unreproduced one-off failure does not belong here; record what the next occurrence needs instead, and reproduce it first.
