# Reproduced, unresolved findings

## A tolerant JSON fallback differs from `parseStreamingJson` on malformed text

- Severity: low. Only malformed text differs, and the pinned reference has no caller of `parseStreamingJson` (grep of `pi/packages/ai/src` finds it only in comments), so no reference code path reaches the difference. `ai.ParseStreamingJSONText` is exported, though, and its doc claims parity with that function.
- Failure: `parseStreamingJSONObject` (`ai/jsonparse.go`) is `parseStreamingJson`'s three-step fallback (strict parse, repair, partial parse) with the port's own partial parser. On 458 adversarial inputs (43 documents plus every prefix), 439 of which the reference parses to an object, 42 differ, all malformed: a missing comma or colon is tolerated (`{"a":1 "b":2}` gives `{"a":1}` where the reference gives `{}`), raw control characters and invalid escapes stay visible (`{"bad":"\d"` gives `{"bad":""}`, the reference `{}`), a loose number is accepted (`{"p":.5}` and `{"plus":+1}` parse where the reference gives `{}`), `NaN`/`Infinity` prefixes give `{}` where `partial-json` gives `null`, a lone surrogate decodes to U+FFFD where the reference keeps the code unit (D253), and trailing whitespace of an unterminated string is kept where `parseStreamingJson` trims it.
- Evidence: the differential is `parseStreamingJson` from the pinned `pi/packages/ai/dist/utils/json-parse.js` against `parseStreamingJSONObject`, one JSONL dump each, compared field by field; every well-formed prefix agrees, the case the 15,679 generated prefixes recorded in `ai/jsonparse.go`'s comment cover (D325 adds the nesting bound).
- Why it is not simply fixed: the port calls the helper where upstream uses `ToolCallArgumentsStream` (the abort-time finalization in `anthropic_stream.go` and the four sibling adapters), and there the tolerated missing comma, kept control character and kept trailing space are exactly the preview `streaming_json.go` produces. One function cannot match both references. Splitting it (streaming rules for the adapters, `partial-json` rules for the exported helper) is the repair, and it needs the extra `partial-json` rules above plus a Node-generated golden corpus; it is not worth new dependencies for a helper nothing in the reference calls.

## A self-referential union skips coercion the reference applies

- Severity: low. The value accepted differs, not whether the call is accepted, and only for a schema that reaches itself without consuming any of the value (a `$ref` cycle through `anyOf`, `allOf`, `not` or `if`), which no real tool schema writes.
- Failure: with `{"$defs":{"loop":{"anyOf":[{"type":"string"},{"$ref":"#/$defs/loop"}]}},"properties":{"a":{"$ref":"#/$defs/loop"}}}`, arguments `{"a":1}` come back as `{"a":1}`, where pi v1.5.2 `b4afdddf` `packages/schema/src/coerce.ts` `convertUnion` returns `{"a":"1"}`: its `passes()` on the recursive branch throws and is caught as `undefined`, so the union tries the string branch and converts. Pier's cycle guard reports the re-entered `(schema, value)` pair as accepted, so `convertUnion` sees a branch that "passes" and keeps the value.
- Evidence: one row of the 758-case differential of `ValidateToolArguments` against `packages/ai/src/utils/validation.ts`; the other 757 match exactly.
- Repair plan: make the check's re-entry answer `false`/unknown for the coercion probe (as the reference's throwing `passes` does) while keeping `true` for the plain check, or port the reference's `entered`/`cuts` stack. It needs care: flipping the guard to `false` would make a genuinely recursive schema reject deep values, so the two callers need separate answers.

## A config shell command spawns a visible console window on Windows

- Severity: low. Windows only, and only when the process has no console of its own (a GUI host embedding pier, or a service). A terminal session inherits the console, so nothing appears and the output is identical.
- Failure: `executeWithConfiguredShell` (`coding/resolveconfigvalue.go`) spawns the configured shell with `exec.CommandContext` and no `SysProcAttr`, so Windows creates a console window for it when the parent has none. The reference passes `windowsHide: true` to its `spawnSync` call (`core/resolve-config-value.ts`), which suppresses that window.
- Evidence: read of both files; the reference option list contains `windowsHide: true`, while `grep HideWindow` finds only `mcp/processgroup_windows.go`, which sets `cmd.SysProcAttr = &syscall.SysProcAttr{HideWindow: true}` for the same reason.
- Repair plan: add a build-tagged `hideConfigCommandWindow(cmd *exec.Cmd)` beside the existing platform files, set `HideWindow` on Windows in that path only (the default-shell path mirrors `execSync`, which does not pass the option), and pin it with a Windows-tagged test like `mcp/processgroup_windows_test.go`. It is not run locally because the test can only execute on Windows.

## The shell environment omits the reference's agent bin-dir PATH entry

- Severity: low. Visible only when something places an executable in `<agentDir>/bin` and a bash command calls it by bare name; pier itself writes nothing there, and the package manager that populates it upstream is out of scope (D41).
- Failure: `shellEnv` (`coding/tools_bash.go`) ports `getShellEnv`'s env copy and the `PI_*` filtering but not its PATH edit. Upstream prepends `getBinDir()`, `<agentDir>/bin`, when the current PATH (under whichever key spells it, `Path` on Windows) lacks that directory, so a command can invoke a tool installed there by name. Pier passes PATH through unchanged.
- Evidence: read of both. `getShellEnv` and `getBinDir` are in `pi/packages/coding-agent/src/config.ts` and `utils/shell.ts`; `grep -rn GetBinDir` finds nothing in the port and no code creates `<agentDir>/bin`.
- Repair plan: thread the session's agent dir into `shellEnv`, compute the bin dir once, find the PATH entry case-insensitively (upstream keeps the existing key's spelling), prepend the bin dir when absent, and pin the three spellings with a table test. The plumbing from `AgentSession` to the bash tool options is what keeps it out of a small change.

## The keybinding manager's introspection API differs in shape and order

- Severity: low. Nothing in the tree serializes the result: `AppKeybindingsManager.GetEffectiveConfig` forwards `GetResolvedBindings` and only tests read it, and `GetConflicts` feeds an on-screen conflict warning whose order carries no meaning.
- Failure: `KeybindingsManager.GetResolvedBindings` returns `map[string][]string`, so a binding with one key is `["ctrl+x"]`; the reference's `keybindings.ts` `getResolvedBindings` returns `keys.length === 1 ? keys[0] : [...keys]`, i.e. the bare string `"ctrl+x"`. `GetConflicts` also sorts its keys and claimant names, while the reference emits conflicts and claimants in `Object.entries` insertion order.
- Evidence: read of both files; the reference's return expression and `for (const [key, keybindings] of userClaims)` loop, against the port's `map[string][]string` result and `sortStrings` calls. The Go map has no insertion order to reproduce, which is why the port sorts.
- Repair plan: if something ever persists or compares the resolved bindings, give the manager a `map[string]any`-style result (string for one key, slice otherwise) and record the sorted conflict order as a D-row next to the other map-order substitutions. Until then the Go shape is the more usable one and the difference is invisible.

## Virtual models can be listed but never routed

- Severity: medium. Nothing in the CLI registers one, but `coding.WithVirtualModels`, `coding.CreateVirtualModel` and `coding.VirtualModelDefinition.Route` are exported for SDK callers, and a registered router is never invoked: its model streams `Virtual model <provider>/<id> must be routed before streaming` from `unroutedStream`.
- Failure: pier ports `virtual-models.ts` (the catalog entry, the provider catalog wrapper, `GetBranchSelection`, `FindLatestResponse`, `GetVirtualModelState`) but not the router. `ModelRuntime.resolveModel` (`pi/packages/coding-agent/src/core/model-runtime.ts:1040`) validates the registration, builds `previous` from `findLatestResponse`, resolves the failed response for a retry, calls `virtual.route(request)`, then requires a physical catalog model with credentials and clamps the thinking level to it; `agent-session.ts` `prepareRequest` supplies `reason`, `state` and `failed` and appends a `pi.virtual-model-state` custom entry whenever the returned state changes. In the port `VirtualModelDefinition.Route` has no caller, `ModelRouteRequest` is never constructed outside tests, and `VirtualModelStateEntry` has no writer, so `GetVirtualModelState` can only read entries that nothing stores.
- Evidence: `grep -rn "\.Route(\|ModelRouteRequest{" --include=*.go` returns only the definitions; `grep -rn "pi.virtual-model-state"` finds the constant alone; `ai/virtualmodels.go` wraps only the catalog and the unrouted stream.
- Repair plan: add a `ResolveVirtualModel` on the model runtime porting the validation and clamping order of `resolveModel`, call it from the request-preparation hook where the port installs its other `prepareRequest` work, pass the branch's stored state in and append the state entry when it changes, and pin the error cases (unregistered, non-physical target, missing credentials) plus a state round trip with a fake router. The request-preparation seam already exists, so the work is the router and its state plumbing.

## `go test ./coding ./cmd` failed once and did not reproduce

- Severity: low until it repeats; it may be a resource-limited environment effect rather than a test bug.
- Failure: one `go test -count=1 ./coding ./cmd` run printed `FAIL` for `./coding` while `./cmd` passed. The harness truncated the output before the failing test name, so the case is unknown.
- Evidence: five later runs were green, including three repeats of the same two-package command and two `go test -count=1 ./...` runs, so it is not deterministic. The audit summary from an earlier session records one similar truncated `./coding` failure that also did not reproduce in nine runs.
- Repair plan: the next occurrence needs the full log, `go test -count=1 ./coding -json` or `-run` bisection, and the test name recorded here. `internal/leakcheck` runs every package's `TestMain`, so a leaked goroutine would name itself with `GODEBUG=tracebackancestors=20`.
