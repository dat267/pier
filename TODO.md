# Reproduced, unresolved findings

## Auto-compaction for a virtual selection (reassessed)

- Severity: low. Nothing was double-compacting in the shipped path; the remaining case needs a selection without a declared window and an assistant message whose model left the catalog.
- Reassessed (audit round 15): the original claim, that a virtual selection never uses the routed model's window, is wrong. `CheckCompaction` sizes the threshold from `modelForMessage(assistant)`, which resolves the physical model a virtual request recorded, so the routed window is honoured wherever an assistant message names it. A threshold check added inside `prepareVirtualRequest` therefore compacted a second time per boundary (measured: two compaction entries where the port had one), and was reverted.
- Fixed instead (`87793422`): when no model supplies a window, `CheckCompaction` now skips. Upstream compares against `undefined - reserveTokens` (NaN, false); the port used a zero window, making the threshold negative and compacting at every boundary. Reachable with a windowless selection once the assistant's model is gone from the catalog. `TestCheckCompactionSkipsAnUnknownContextWindow` pins it: two summarization streams before, none after.
- Open, if ever pursued: `maybeAutoCompact` and `CheckCompaction` disagree for a zero window (`maybeAutoCompact` skips, which now matches upstream). No reachable divergence is known beyond the fixed one.

## A stress-gate run failed the RPC chaos test on a session write

- Severity: low until it is understood; it is a test failure in CI, not a confirmed product bug.
- Failure: in CI run 43827491162, the `race stress` step (`go test -race -count=2 -cpu=1,4 -shuffle=on -timeout 900s ./agent ./coding ./coding/interactive ./mcp`, shuffle seed 1794816114167051316) failed in `./coding`: `TestRPCAnswersEveryCommandOnceUnderAnInterleavedLoad` reported `the server stopped with session append failed (/tmp/TestRPCAnswersEveryCommandOnceUnderAnInterleavedLoad1767583622/003/other.jsonl): open .../other.jsonl: file exists`. A session manager whose file is missing records an uninitialized write state, so its first save claims the file with `O_EXCL`; the message means a claim found the file already there.
- Evidence: the CI log above. Not reproduced locally: one full `go test -race -count=2 -cpu=1,4 -shuffle=on ./coding` (green), one with the same seed (green), and six focused `-count=2 -shuffle=on` runs of the test (green). The test switches to one fixed path from a random 200-command stream, so the collision needs a particular interleaving.
- Refinement (audit round 11): upstream shares the throw. `_persist` in `core/session-manager.ts` creates the file with `openSync(sessionFile, "wx")` exactly once and lets an `EEXIST` escape, so the exclusive claim and its error are parity, not a port defect. What upstream does not have is a write queue shared between session managers: `rpcRuntime.newSessionManager`/`forkManager` pass `current.GetWriteQueue()` to the replacement, so a write enqueued for the outgoing manager can run against a path the incoming manager created. That is now the leading candidate, and the probe it needs is a log in `writeSessionEntriesExclusive` recording the path, the manager's session id and the enqueuing stack, then the stress loop.
- Fixed (audit round 11-12): neither replacement path drained the shared write queue, so a write enqueued for the outgoing session could run after the replacement was bound and hit the replacement's file. `a0165674` flushes in `rpcRuntime.installSession` and `interactive.App.teardownCurrentSession`; `TestRPCSwitchSessionDrainsTheOutgoingWriteQueue` blocks the queue's worker, queues an append, and requires the switch to stay unanswered until the append is on disk. That leaves two ways the original message could still appear: a write enqueued *after* the flush (a detached worker appending during the switch), or two managers opened on the same path before either wrote it. The debug step below is for those.
- Repair plan: reproduce first. Run the stress command in a loop with `PIER_DEBUG_WRITE=1` and a temporary stack print in `SessionManager.recordWriteResult` (the message is built there), so the failing caller is known before anything is changed. Two candidates to check once reproduced: two managers opened on the same path before either writes it, or a queued write from the previous session landing after `switch_session` installed the new manager. `writeSessionState.rewrite` should then skip the exclusive claim when the file already exists, with a unit test that drives the reproducing sequence.

An unreproduced one-off failure does not belong here; record what the next occurrence needs instead, and reproduce it first.
